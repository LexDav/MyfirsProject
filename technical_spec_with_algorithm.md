# Telegram-бот «LegalTech ТН ВЭД» (MVP)

## 1. Общая информация

### 1.1 Название проекта
Telegram-бот «LegalTech ТН ВЭД» — интеллектуальный помощник для автоматизированного подбора кода ТН ВЭД. Система оценивает риски некорректной классификации и помогает участникам внешнеэкономической деятельности (ВЭД) выбирать верный код.

### 1.2 Краткое описание
Бот реализуется на платформе Telegram. Пользователь описывает товар свободным текстом или отвечает на последовательный опрос. Интегрированный алгоритм (нейронная модель/правила) анализирует запрос, предлагает один или несколько кодов ТН ВЭД и отображает вероятность корректности каждого варианта.

Внесение данных возможно в двух режимах:
- **Light-режим (опросник)** — бот задаёт уточняющие вопросы по готовой анкете; вопросы подобраны таким образом, чтобы минимизировать количество шагов и повышать точность определения кода.
- **Expert-режим** — пользователь сразу предоставляет максимально полное описание товара (характеристики, назначение, материал, изображение). Алгоритм обрабатывает введённый текст и возвращает коды без подробных уточнений.

Система использует актуальную редакцию Единой товарной номенклатуры внешнеэкономической деятельности (ТН ВЭД) Евразийского экономического союза (ЕАЭС), которая включает 21 раздел и 97 групп товаров. Классификатор регулярно обновляется решениями Совета ЕЭК (в 2025 году появились новые коды и подгруппы); бот регулярно актуализирует данные.

### 1.3 Цель проекта и целевая аудитория
**Цель проекта** — обеспечить быструю и достоверную поддержку при определении кода ТН ВЭД, снизить риск ошибок классификации и связанных санкций. Правильный код влияет на размер таможенных пошлин, НДС, акцизов и применимость разрешительных документов; неверная классификация влечёт штрафы по ст. 16.2 КоАП РФ.

**Целевая аудитория:**
1. импортеры, экспортеры и компании-участники ВЭД (юридические и физические лица), оформляющие декларации самостоятельно;
2. таможенные представители и брокеры, оптимизирующие процессы и обучающие сотрудников;
3. специалисты юридических и логистических служб;
4. контролирующие органы — как потенциальные пользователи для сверки классификации.

## 2. Функциональные требования

### 2.1 Базовый функционал (MVP)
1. **Определение кода ТН ВЭД.** Пользователь описывает товар (в режиме Light или Expert), а бот возвращает один или несколько вероятных кодов ТН ВЭД с уровнем уверенности. Система учитывает последнюю версию классификатора: 21 раздел и 97 групп и новые коды, введённые с 2025 года.
2. **Опросник (Light-режим).** Для пользователей без опыта бот задаёт уточняющие вопросы.
   
   Предварительный список вопросов для MVP:
   
   | № шага | Вопрос бота | Примечание |
   | --- | --- | --- |
   | 1 | Хотите проверить правильность имеющегося кода ТН ВЭД? | Да/Нет. Если «Да», то бот просит ввести код, наименование и, при наличии, изображение товара; затем сверяет код с классификатором. |
   | 2 | Укажите полное наименование товара (официальное название, артикул, модель). | Текстовое поле. |
   | 3 | Есть ли изображение? | Если ответ «Да», бот запрашивает изображение (фото, скан). |
   | 4 | К какой категории (разделу/группе) относится товар? | Пользователь выбирает из выпадающего списка разделов. Для MVP бот может ограничиться простыми группами (например, группы 01, 08, 10, 44, 47) для демонстрации. |
   | 5 | Назначение товара? | Уточняет, для чего предназначен товар (производственная деталь, личное потребление, комплектующая, сырьё и т.д.). |
   | 6 | Из какого материала изготовлен товар? | Перечень вариантов; помогает сузить классификацию. |
   | 7 | Форма поставки: готовое изделие, полуфабрикат, запчасть, набор или комплект? | Выпадающий список. |
   | 8 | В какой упаковке поставляется товар (коробка, контейнер, блистер и т. п.)? | Учитывается при классификации для некоторых групп. |
   | 9 | Дополнительная информация | Свободное поле для особенностей (сертификаты, функции, составные части). |

   Если после шагов 1–4 бот получает однозначный результат, остальные вопросы пропускаются. Диалог можно закрыть в любой момент командой `/cancel` (ответы будут сброшены). Анкета адаптивна: бот сам выбирает следующий вопрос на основании промежуточного результата.
3. **Expert-режим.** Пользователь сразу вводит подробное описание товара; бот анализирует текст (и изображение, если приложено) и предлагает возможные коды без пошаговых вопросов.
4. **Проверка имеющегося кода.** Пользователь может проверить корректность введённого кода (команда `/check <код>`). Бот возвращает официальное описание кода, раздел, группу и информирует об актуальности (учитывает изменения в классификаторе). В случае устаревания кода бот предлагает новые позиции.
5. **Оценка рисков.** Для каждого предложенного кода бот отображает вероятность корректности классификации (например, 85 %) и сообщает пользователю, что неверное декларирование может повлечь штрафы (физические лица — от 10 000 до 20 000 руб., юридические — от 50 % до 200 % суммы неуплаченных пошлин). Алгоритм вычисляет риски на основе уверенности модели, полноты описания и совпадения с нормативными источниками.
6. **История запросов.** Бот сохраняет сведения о предыдущих запросах (код, дата, результат) и позволяет пользователю просмотреть историю (`/history`). В истории не сохраняются отменённые сессии.
7. **Управление режимом и завершение диалога.** Пользователь в любой момент может сменить режим или завершить диалог. Команды:
   - `/start` — приветственное сообщение и выбор режима (Light/Expert).
   - `/help` — справка с описанием команд.
   - `/classify` — запуск процесса классификации (в текущем режиме).
   - `/check` — проверка существующего кода.
   - `/history` — просмотр истории запросов.
   - `/cancel` — завершение текущего диалога и очистка введённых данных.
   - `/settings` — (опционально) включение/выключение уведомлений о новостях.

### 2.2 Дополнительный функционал (перспективное развитие)
2.2.1 **Интеграция с нормативными источниками.** Подключение к официальным базам (портал ЕЭК, классификационные решения ФТС, реестр классификаций, пояснения к ТН ВЭД, судебная практика). Бот может выдавать ссылки на нормативные документы и решения Комиссии ЕЭК о классификации конкретных товаров. Например, для легковых электромобилей применяются обновлённые пояснения: Рекомендация Комиссии ЕЭК от 23.09.2025 № 25 изменила примечание к позиции 8703 80 000 2, заменив её на позиции 8703 80 000 3 и 8703 80 000 5.

2.2.2 **Ставки таможенных пошлин.** Вывод информации о действующих ставках импортных пошлин, акцизов и НДС для выбранного кода. Изменение ставок в 2025 году связано с перераспределением позиций и усилением контроля.

2.2.3 **Экспорт истории и статистика.** Экспорт запросов в форматах CSV/XLS; сбор анонимной статистики для анализа популярности групп товаров.

2.2.4 **API-интеграция.** Разработка API для подключения внешних сервисов, интеграций с корпоративными системами, ERP, таможенными брокерами. На стадии MVP API не реализуется, но закладывается архитектура для расширения.

## 3. Технические требования

### 3.1 Платформа и инструменты
1. Мессенджер: Telegram; используется Telegram Bot API для приёма/отправки сообщений.
2. Язык программирования: Python 3.10+.
3. Фреймворк бота: aiogram (асинхронный фреймворк); допускается использование pyTelegramBotAPI как альтернативы.
4. Модели и библиотеки: для NLP — Hugging Face Transformers, spaCy; для машинного обучения — scikit-learn, PyTorch или TensorFlow; для анализа изображений — torchvision. Модель обучают на наборах данных ТН ВЭД, а также на примерах, сформированных командой.

### 3.2 Архитектура
Система строится по клиент-серверной схеме. Основные компоненты:
1. **Telegram Bot Handler.** Обрабатывает входящие сообщения (webhook или long-polling); определяет команду, режим (Light/Expert), вызывает соответствующие функции и формирует ответы. Команды `/query`, `/remove query` и `/reply` оставлены в описании как внутренние функции для расширения.
2. **Database/Storage.** Хранит информацию о пользователях (chat_id, регистрационные данные), запросы и результаты, логи работы бота. Для MVP используется встроенная база SQLite; при масштабировании предусмотрен переход на PostgreSQL. Хранение осуществляется в соответствии с принципом минимизации данных; в истории сохраняются только необходимые поля (код, дата, описание).
3. **Cron-процедуры.** Обеспечивают регулярные запросы к внешним источникам (например, обновление классификатора, ставок пошлин, пояснений). Cron используется для автоматической синхронизации данных и отправки уведомлений пользователям (если активирована функция обновлений).
4. **API-client.** Модуль для обращения к официальным источникам:
   - классификатор ТН ВЭД ЕАЭС (портал ЕЭК),
   - пояснения к ТН ВЭД,
   - реестр классификационных решений,
   - судебная практика (на перспективу).

   Запросы осуществляются через открытые API или загруженные справочники. В 2025 году в классификатор были добавлены новые коды и перераспределены некоторые позиции, поэтому актуализация данных обязательна.
5. **Filter & Formatter.** Форматирует ответы бота: отображает заголовок, найденный код, название товара, вероятность, ссылку на нормативный источник, ставку пошлины и сообщение об оценке риска. Вывод структурирован так, чтобы юридический язык сочетался с понятностью для пользователя.

### 3.3 Хранение данных
1. **База данных.** Для MVP — SQLite. Таблица `users` хранит chat_id, имя пользователя, дату регистрации. Таблица `queries` содержит user_id, заполненные ответы опросника, предложенные коды, вероятность и дату. Таблица `history` хранит архив запросов. При переходе к промышленной версии планируется использование PostgreSQL.
2. **Конфиденциальность.** Личные данные (chat_id) используются только для идентификации сессии. Токен бота хранится в переменных окружения; доступ к базе ограничен правами, необходимыми для работы приложения.

### 3.4 Производительность
Бот должен отвечать на запросы в течение 1–2 секунд. Обработка запроса и расчёт вероятности выполняются асинхронно, чтобы поддерживать одновременную работу нескольких пользователей. Для ускорения используются кэширование часто запрашиваемых кодов и оптимизация моделей (ограничение длины описания, предзагрузка embeddings).

### 3.5 Безопасность
Все взаимодействия осуществляются через HTTPS. Логирование ведётся с учётом законодательства о персональных данных. Собираются только минимально необходимые данные (описание товара, ответы опросника, идентификатор пользователя). Бот соблюдает запрет на спам и рассылку персональных данных без согласия.

## 4. Интерфейс и команды

### 4.1 Основные команды
| Команда | Назначение |
| --- | --- |
| `/start` | Приветствие, выбор режима (Light или Expert), краткое описание возможностей бота. |
| `/help` | Выводит список команд и разъясняет назначение каждой. |
| `/mode` | Позволяет переключить режим работы бота: Light (опрос) или Expert (свободный ввод). |
| `/classify` | Запуск процесса классификации (в текущем режиме). В режиме Light запускает опросник; в режиме Expert предлагает ввести описание товара. |
| `/check <код>` | Проверить имеющийся код ТН ВЭД; бот возвращает официальное описание, актуальность и предупреждение о возможных изменениях. |
| `/history` | Показывает историю запросов пользователя. |
| `/cancel` | Завершает текущий диалог, очищает введённые данные и возвращает пользователя в главное меню. |
| `/settings` | Настройки уведомлений и подписки на новости (опционально). |

Вероятность ошибки классификации составляет 27 %. Для уточнения результата укажите: технологию аккумулятора (AGM, GEL, EFB), ёмкость и наличие обслуживания. Желаете уточнить? (Да/Нет)

## 6. Технологический стек
1. **Backend:** Python 3.10+, фреймворк aiogram/pyTelegramBotAPI. Используются библиотеки для NLP (Transformers, spaCy) и машинного обучения (scikit-learn, PyTorch/TensorFlow).
2. **Хранилище:** SQLite для MVP; PostgreSQL для масштабирования. Таблицы: users, queries, history, logs.
3. **Инфраструктура:** VPS/облачный сервер с поддержкой Python и TLS; репозиторий GitHub/GitLab; CI/CD (Docker, GitHub Actions). Мониторинг через логирование и системные средства.
4. **Интеграции:** Telegram Bot API; в перспективе — API ЕЭК для загрузки классификатора, сервисы для получения ставок пошлин; базы судебной практики.

2. Разработчик AI/ML — разработка и обучение модели классификации (NLP-анализа описания товара). Является критически важным ресурсом; его задачи (настройка модели, проверка результатов) запланированы на начало проекта.
3. Разработчик интерфейса (Telegram-бот) — настройка логики бота (обработчики команд), проработка диалогов с пользователем, разработка текста сообщений и интерфейса взаимодействия. Также отвечает за подготовку презентационных материалов.
4. Тестировщик и DevOps — (при необходимости) дополнительный участник команды может взять на себя настройку окружения, мониторинг и тестирование бота перед релизом.
5. Ресурсы: проект реализуется силами команды с возможностью привлечения сторонних специалистов (в соответствии с хакатонным форматом и требованиями бюджетной эффективности).

## 8. Критерии приемки

### 8.1 Функциональные критерии
1. Пользователь может выбрать режим (Light/Expert), ввести описание товара и получить список предложенных кодов ТН ВЭД с оценкой вероятности.
2. В режиме Light бот задаёт уточняющие вопросы, поддерживает возможность досрочного завершения сессии командой `/cancel`.
3. В режиме Expert бот корректно обрабатывает свободный текст и изображение (если приложено).
4. Команда `/check` проверяет имеющийся код и сообщает об актуальности, учитывая изменения в пояснениях (например, для кодов 8703 80 000 2/3/5).
5. Команды `/start`, `/help`, `/mode`, `/classify`, `/history`, `/cancel` работают без ошибок; история запросов отображается корректно.

### 8.2 Технические критерии
1. Время ответа на запрос не превышает 1–2 секунд; бот поддерживает несколько одновременных сессий.
2. База данных хранит историю запросов без потерь; логирование ошибок и действий осуществляется.
3. Обновление классификатора (cron) выполняется по расписанию; информация о новых кодах, пояснениях и ставках пошлин актуализируется (по состоянию на 2025 год и далее).
4. Система защищает данные пользователя (использование HTTPS, ограничение доступа к базе, хранение токена в защищённом хранилище).

### 8.3 Пользовательские критерии
1. Интерфейс бота интуитивно понятен; команды и вопросы формулируются на юридическом, но доступном языке (без неформальной лексики).
2. Ответы бота содержат чёткие формулировки кода, наименования товара и вероятности; присутствуют ссылки на нормативные документы (при использовании дополнительных функций).
3. Пользователь может легко завершить диалог, переключить режим или проверить ранее введённый код; диалог не «зависает» после завершения.

## 9. Соответствие нормативной базе
1. Проект использует актуальный классификатор ТН ВЭД, утверждённый решением Совета ЕЭК от 14 сентября 2021 г. № 80 (с учётом изменений до 2025 года). Номенклатура включает 21 раздел и 97 групп.
2. Классификация обновляется по решениям Совета ЕЭК и рекомендациям Коллегии ЕЭК. В 2025 году были введены новые коды и подгруппы, а участники ВЭД обязаны указывать более подробную информацию в декларации.
3. Пояснения к ТН ВЭД также актуализируются: например, в сентябре 2025 года изменения касались легковых электромобилей (пометка к позиции 8703 80 000 2 заменена на 8703 80 000 3 и 8703 80 000 5).
4. Проект учитывает административную ответственность за некорректную классификацию (ст. 16.2 КоАП РФ), где для физических лиц штраф составляет 10 000–20 000 руб., для юридических — от 50 % до 200 % суммы неуплаченных пошлин. Приложение предупреждает пользователя о рисках.

# Текстовый алгоритм определения кода ТН ВЭД

## Входные данные
Пользователь вводит описание товара (свободным текстом, с характеристиками, назначением, параметрами).

## Шаг 0. Выбор режима работы
Система предлагает пользователю выбрать режим определения кода ТН ВЭД:
- Light-режим (с уточняющими вопросами),
- Expert-режим (без уточняющих вопросов).

## Основной процесс (общий контур)

### Шаг 1. Получить описание товара
Система фиксирует исходные данные от пользователя: описание, доступные документы/характеристики (если переданы).

### Шаг 2. Извлечь признаки товара
Система извлекает признаки, необходимые для классификации товара.
- Если выбран Light-режим — система может задавать вопросы, чтобы уточнить признаки.
- Если выбран Expert-режим — система не задаёт вопросы и работает только с тем, что уже предоставлено пользователем.

### Шаг 3. Определить код ТН ВЭД по правилам
На основе извлечённых признаков система выбирает наиболее подходящий код ТН ВЭД (с детализацией «до 10 знаков»).

### Шаг 4. Проверить альтернативные коды
Система проверяет, какие ещё коды могут подходить при близких/неполных признаках, и формирует список возможных альтернатив.

### Шаг 5. Сформировать разъяснения по выбранным кодам
Система формирует объяснение выбора:
- почему выбран основной код,
- почему альтернативы менее предпочтительны,
- какие признаки оказались ключевыми.

### Шаг 6. Выдать результат пользователю
Система выводит пользователю:
- наиболее вероятный код,
- альтернативные коды,
- процентную вероятность релевантности для каждого предложенного кода.

## Внутренняя логика извлечения признаков (детальный блок)
Извлечение признаков выполняется последовательно по этапам (каждый этап — это «ветка уточнений»):
1. Определение категории товара (техника/оборудование, химия, текстиль, продукты питания, сырьё и т. д.).
2. Определение функционала товара — что делает товар и какую функцию выполняет (фильтрует, охлаждает, приводит в движение, является упаковкой и т. п.).
3. Определение способа изготовления / степени переработки / принципа работы — сырьё vs полуфабрикат vs готовое изделие; механический/электронный/химический принцип.
4. Определение материала товара — из чего изготовлен товар (и при необходимости — из чего изготовлены его основные части).
5. Определение назначения товара — бытовой/промышленный, медицинский/строительный, для транспорта и т. п.
6. Определение количественных или качественных параметров товара:
   - количественные: мощность, объём, размер, производительность и т. п.;
   - качественные: особые тех. характеристики, форма товара, способ перевозки, если эти параметры влияют на код.

На каждом этапе система может:
- задать вопрос для уточнения признака (в Light-режиме),
- либо пропустить этап, если признак не нужен или уже известен.

## Правила применения алгоритма (логика пропусков/вопросов)
Алгоритм применяется гибко — не все этапы обязательны:
- оценка этапов делается исходя из уже имеющегося набора признаков;
- если конкретный признак не влияет на выбор кода, этап его извлечения можно пропустить;
- вопрос можно не задавать, если признак уже можно извлечь из описания/данных.

Для количественных характеристик система проверяет:
- используется ли этот показатель в структуре кода/описания позиции;
- есть ли порог/диапазон (например «до / более»);
- влияет ли значение на конкретный код.

Качественные критерии — это не «качество товара», а именно особые тех. характеристики / форма / способ перевозки, если это значимо для классификации.

При выдаче результата система обязана показывать процент релевантности по каждому коду. В Expert-режиме вопросы не задаются.

## Алгоритм в виде «текста-процедуры» (для ТЗ)
1. Система запрашивает у пользователя описание товара и предлагает выбрать режим: Light или Expert.
2. Система принимает описание товара.
3. Система извлекает признаки товара, проходя по этапам: категория → функционал → изготовление/переработка/принцип → материал → назначение → количественные/качественные параметры.
4. Если выбран Light-режим, то при отсутствии критических признаков система задаёт уточняющие вопросы (и пропускает те признаки, которые не влияют на итоговый код).
5. Если выбран Expert-режим, то система извлекает признаки только из полученного описания без уточняющих вопросов.
6. На основе набора признаков система подбирает наиболее вероятный код ТН ВЭД (до 10 знаков).
7. Система формирует альтернативные коды (если есть конкурирующие ветки классификации).
8. Система формирует разъяснение (какие признаки привели к выбору кода и почему альтернативы менее предпочтительны).
9. Система выводит пользователю основной и альтернативные коды с процентом релевантности каждого варианта.
