## 2. Архитектура бота

### Два режима работы

- **Light-режим** — пошаговый диалог. Бот задаёт уточняющие вопросы по одному за сообщение. Для пользователей, у которых недостаточно данных.
- **Expert-режим** — единоразовый запрос. Пользователь даёт полное описание, бот выдаёт код без вопросов. Для опытных участников ВЭД.

### Команды Telegram

- `/start` — приветствие + выбор режима
- `/help` — справка
- `/classify` — запуск классификации
- `/check` — проверка существующего кода
- `/history` — история запросов
- `/cancel` — завершение диалога

### Алгоритм классификации (7 шагов)

0. Определение режима (Light/Expert)
1. Получение описания товара
2. Определение группы и товарной позиции (4 знака)
3. Извлечение признаков товара (**внутренний шаг**, не выводится пользователю)
4. Определение 10-значного кода (спуск по иерархии)
5. Проверка альтернативных кодов (ОПИ 3)
6. Формирование ответа (строго по формату раздела 7)
7. Обработка недостаточности данных

**Что сделано:**

- Через Prompt Architect (3C-фреймворк) разработана системная инструкция `system_prompt_tn_ved_v3.md`
- Через 3 итерации с обратной связью от пользователя уточнены:
  - Иерархическая структура кода ТН ВЭД (2→4→6→8→10 знаков)
  - Интеграция ОПИ 1–6 в алгоритм
  - Формат ответа: таблица (код / наименование / вероятность / ставка) + обоснование
  - Критерии вероятности: Высокая / Средняя / Низкая
  - Запреты: коды только из файла, нет вопросов в Expert, профессиональный тон
  - Примеры контрольных вопросов для позиций 8408 и 8418
  - Дисклеймер (ссылка на Приказ Минфина 181н)

**Ключевые решения:**
- Бот использует GPT с файлом базы знаний as-is (не RAG)
- North Star = «правильный код, которому пользователь может доверять и обосновать перед таможней»
- В ответе — только один основной код (не список альтернатив), но с указанием, если альтернативы возможны
- Правило: два кода с вероятностью «Высокая» невозможны — разрешается через ОПИ 3

## 5. Открытые задачи и следующие шаги

### 5.1. По системной инструкции (prompt engineering)

- **Тестирование v5** — прогнать на тестовых кейсах из `Классификация_2.md` и проверить, что все 7 дефектов закрыты
- **Тест PATCH-7** — убедиться, что модель корректно применяет правило согласованности вероятности и обоснования (тестовый вход: встраиваемый холодильник R600a 313 л)
- **Edge cases** — проверить поведение на: товар вне Группы 84, расхождение описания и позиции, минимальное описание в Expert-режиме
- **Расширение базы** — v5 заточена под Группу 84; при расширении на другие группы потребуется адаптация раздела 3 (база знаний) и раздела 6 (контрольные вопросы)

### 5.2. По Telegram-боту (из презентации проекта)

- Встроить LLM (ChatGPT Plus) в бота
- Light-режим: переделать в формат диалога (сейчас выполнял функцию /check)
- Expert-режим: реализовать логику «недостаточно данных → предложить Light»
- Разработать критерии достаточности данных для Expert-режима
- Исправить баги при переключении режимов и команде /classify

## 6. Ключевые принципы (для сохранения контекста)

1. **Единственный источник кодов** — файл `ru_84_2022_21.09.2025.md`. Модель не может брать коды из обучающих данных.
2. **Код выдаётся ВСЕГДА** в Expert-режиме, даже при недостатке данных (с пониженной вероятностью).
3. **В Expert — никаких вопросов** ни в какой форме. Только стандартная рекомендация на Light.
4. **Шаг 3 — внутренний**. Пользователь видит только формат раздела 7.
5. **Вероятность согласована с обоснованием**. «Данных не хватает, но это не влияет» при вероятности ниже «Высокой» = ошибка.
6. **Три уровня вероятности** допустимы в Expert. Рекомендация на Light — только когда код невозможно выдать даже с «Низкой».
7. **Тон** — строго профессиональный, юридически корректный. Никакого разговорного стиля.
